# Upgrading to v1.5.0

v1.5.0 gives a project genres and tags, caps its title at 80 characters, and keeps one picture: its logo.

## Do I need to act?

**Required** for a client that updates projects, or that uses project pictures: updates now need two more fields, and the picture routes are gone. A client that only reads projects keeps working, as long as it ignores unknown fields and does not read `backgroundVersion`.

## Send tags and genres on every update

`projectUpdate` now requires `tags` and `genres`, so an update cannot wipe them by omission. An empty list clears one. `projectCreate` takes both as optional. Each list holds at most 10 items of 1 to 24 characters, with no duplicates.

```diff
 await projectUpdate(api, accessToken, {
   id,
   title,
   premise,
   language,
+  tags,
+  genres,
 });
```

A project read carries both, always, empty when unset.

## Keep project titles to 80 characters

A title over 80 characters now answers 400 on create and on update. A stored title between 81 and 200 characters stays readable, and has to be shortened at its next update.

## Move from pictures to the logo

The background is removed, with every stored background and `backgroundVersion`. The picture routes become logo routes:

| v1.4.0                                                   | v1.5.0                                   |
| -------------------------------------------------------- | ---------------------------------------- |
| `PUT /v1/project/picture?projectID=<id>&picture=logo`    | `PUT /v1/project/logo?projectID=<id>`    |
| `GET /v1/project/picture?projectID=<id>&picture=logo`    | `GET /v1/project/logo?projectID=<id>`    |
| `DELETE /v1/project/picture?projectID=<id>&picture=logo` | `DELETE /v1/project/logo?projectID=<id>` |

```diff
-await projectPictureUpdate(api, accessToken, { projectID, picture: ProjectPicture.Logo }, file);
+await projectLogoUpdate(api, accessToken, { projectID }, file);
```

`ProjectPicture`, `ProjectPictureSchema` and `PROJECT_PICTURE_RULES` are gone. `PROJECT_LOGO_RULES` replaces the last one, and `PictureRefusal.Ratio` is gone, since a logo has no ratio.

## Upload a logo of any shape

A logo now takes any aspect ratio, at most 128 pixels tall and 256 KiB, as a still WebP, JPEG or PNG. A logo past that size answers 422 with the `size` reason, where it answered 400. PNG keeps transparency in browsers that cannot encode WebP.

## Notes

The migration renames `project_pictures` while v1.4.0 still serves, so that release's project reads fail until the rollout ends. No client called them when this shipped.

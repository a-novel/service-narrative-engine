# Upgrading to v1.3.0

v1.3.0 limits how fast each user reads generation calls. The service now sends each user's caps to [GenAI](https://github.com/a-novel/service-genai), tells why a call failed, and reports each user's usage under their caps.

## Do I need to act?

**Required** for a client that reads a call more than twice a second per user, through `GET /v1/generation` or `GET /v1/generation/stream`: past that pace, the routes answer 429. A deployment also upgrades GenAI first, as [Upgrade GenAI first](#upgrade-genai-first) describes. The other changes add fields and a route, so a client that ignores them keeps working.

## Read a call at most twice a second

`GET /v1/generation` and `GET /v1/generation/stream` each take 2 requests a second per signed-in user, on budgets of their own. One more answers 429 with `Retry-After`: wait that many seconds, then read again. `REST_RATE_LIMIT_GENERATION_READ` sets the pace.

```diff
 for (;;) {
   const result = await generationGet(api, accessToken, { id });
   if (result.status !== GenerationStatus.Pending && result.status !== GenerationStatus.Running) break;
-  await new Promise((resolve) => setTimeout(resolve, 200));
+  await new Promise((resolve) => setTimeout(resolve, 500));
 }
```

`generationStream` reads a call that cannot stream once a second by default, which stays within the limit. A `pollInterval` under 500 milliseconds goes past it.

## Read the failure class before resending

A failed call carries `failureClass`, typed as `GenerationFailureClass` in the JS client. It says whether resending the request may succeed:

| Class             | Resend                                                                                             |
| ----------------- | -------------------------------------------------------------------------------------------------- |
| `rejected`        | Fails again: the provider refused the call itself.                                                 |
| `provider_failed` | May succeed.                                                                                       |
| `not_started`     | May succeed, at no extra cost: the provider never ran the call.                                    |
| `outcome_unknown` | May wait: the call counts toward the user's concurrency for 15 minutes.                            |
| `invalid_output`  | Runs the call again, under a new id: the output was refused, cut short or broke its output schema. |

A call GenAI failed before it classified failures carries no class. GenAI no longer retries a call, so a client resends the request to retry it.

## Show the room left under the caps

`GET /v1/generation/usage`, or `generationUsage(api, accessToken)` in the JS client, returns the caller's caps and what the caller consumed under them: the calls in flight, and the tokens consumed over each window. A submit refused for a token window now answers 429 with `Retry-After` when GenAI knows when the window frees usage.

## Upgrade GenAI first

The service sends each user's caps with every submit, and reads usage summaries, which GenAI serves from v0.9.0. Deploy GenAI v0.9.0 or later before this release. An older GenAI ignores the caps, limits users by its own caps file instead, and answers the usage route with 500.
